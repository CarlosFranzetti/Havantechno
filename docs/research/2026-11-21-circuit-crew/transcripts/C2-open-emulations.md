## 0. How to read this file, and what limited it

Tags: **READ** = I fetched the page or file and it says so (URL given; GitHub files were read through the Firecrawl "github-com repositories/file" and "repositories/repo" providers, which fetch raw.githubusercontent.com and the GitHub API; plain `curl` to github.com and api.github.com is refused in this session with "GitHub access to this repository is not enabled", so no `curl` reads were possible). **SNIPPET** = a search result's summary only. **MEMORY** = my recollection, unverified.

Budget used: 15 searches, about 12 page or file reads (many batched). The Firecrawl account then ran out of credits ("Daily MCP credits refresh in 9h 46m"), so the last batch (a1k0n/303, io-808, Vult, ensemble-chorus, string-machine, AT303 page) was refused and is NOT read. Section 9 lists everything left unread. Licences below are the GitHub API's SPDX field plus any LICENSE or README text I read; where the two differ I say so.

Who validated against what is the question that matters most for the owner's aim ("closer to Arturia's methods"), so every table has a "validation" column and the honest answer is mostly "none stated".

## 1. The five best finds in one paragraph

1. **CA-72** (idlefoundry/ca-72, GPL-3.0, Rust, created 3 Oct 2026, pushed 21 Nov 2026): Minimoog Model D voice solved from SPICE netlists transcribed from service documents, real-time models derived from the ngspice runs and checked against them, then calibrated against a hardware reference. Nothing else open comes near it for the Model D. (READ)
2. **JC303's `dfl_DiodeLadderFilter.h` and `dfl_TB303OutputNetwork.h`** (midilab/jc303, files AGPL-3.0-or-later, (C) 2026 David Lowenfels): a diode-ladder 303 filter and the 303 output network written in 2026 on top of the Open303 interface, under exactly this app's licence. (READ, header only)
3. **KR-106** (kayrockscreenprinting/ultramaster_kr106, GPL-3.0, C++/JUCE): a documented Juno-6/60/106 voice with an OTA-saturated TPT ladder standing in for the IR3109, DCO curvature, per-voice tolerance and an MN3009 BBD chorus, with per-model parameter curves. (READ, DSP_ARCHITECTURE.md)

Runner-up: eh2k's TR-909 kit for DrumSynth, whose README states fitted numbers against a circuit simulation and a recording and documents the 909 ROM read rates. (READ)

**Licence trap in one line:** several promising repos have no licence (schollz/juno-60, Faug, Yocto-V2.0, SuperOS-808, squares-and-circles per the API); a no-licence repo is all rights reserved and cannot be ported. Details in section 8.

### 303 verdict

- **Current engine:** Open303's TeeBeeFilter in TB_303 mode is a behavioural ladder fitted by ear, not a circuit solve. It is still the best-validated-by-use choice, but it is not the best model.
- **PORT part:** `src/dsp/open303/dfl_DiodeLadderFilter.h` (56 KB) and `dfl_TB303OutputNetwork.h` from JC303 into `classics-processor.js`, behind the existing filter interface (the header says it keeps TeeBeeFilter's public interface, so the swap is small). Before porting: read the body to find out whether it is a zero-delay-feedback solve, what it iterates, and what it costs per sample. Add a THIRD_PARTY row. Licence consequence: AGPL-3.0-or-later into AGPL-3.0-or-later, no friction. Do not port other JC303 files wholesale (they are GPL-3.0 and MIT mixtures; fine, but unneeded).
- **Accent network:** JC303 exposes the accent capacitor time (15 ms stock). The app already carries Whittle's and Stinchcombe's analyses; this is a cross-check.
- **Not found:** an open 303 with validation against a real unit. Open303's lineage is by ear. The 303 verdict is therefore "port the diode ladder, then validate against C1's schematic values and any recording the owner has".

### 808 verdict

- **No complete open circuit-level 808 exists.** The nearest: Werner's papers (bass drum fully analysed, cymbal analysed; no released code found), WDR-8 for the snare only, and per-voice SPICE work that nobody has published as code that I could find.
- **Current engine:** `drums.js` is already fitted to the service manual's tables and the two Werner papers. That is the right base.
- **PORT part:** the snare's two shell resonators and envelope generator as WDF, from WDR-8 plus WaveDigitalFilters/TR_808/SnareResonator, rewritten in JS (about 5 sub-circuits). Both GPL-3.0 (WDR-8 per its README).
- **REVERSE-ENGINEER from the schematic:** everything else (toms, claps, rim, cowbell, clave, maracas, congas, hats), using chowdsp_wdf (BSD-3-Clause) as the pattern, and the service manual's schematics that C1 documents. The bass drum can be rebuilt straight from the DAFx-14 block equations (the paper gives transfer functions per block; SNIPPET of its tables) with no licence issue beyond CC BY attribution (already in THIRD_PARTY).
- **Validation:** the only comparison data found are SPICE runs. The app's own `tools/drums-score.js` (86 pass, 19 fail on 11 Nov per CLAUDE.md) is a stricter bench than anything published.

### 909 verdict

- **Current engine** (andremichelle constants plus the service-note tables) stays as the base.
- **Use eh2k's published numbers as a second bench** (and compare with `tools/drums-score.js`); they are the only 909 figures stated against a circuit simulation. The hat read rates (30540 Hz and about 34450 Hz) are directly relevant to any ROM-playback hats the owner later chooses.
- **REVERSE-ENGINEER the analogue voices from the service notes** (kick, snare, toms, rim, clap): no open circuit-level 909 exists. A SPICE pass (C3's workflow) is the way to get a reference, as eh2k did.
- **Licence:** eh2k's repo has no machine-readable licence; take numbers only, as facts, and ask the author about the code.

### Juno verdict

- **Current engine** (Junox numbers, Juno60 measurements, own processor) is good on tables and weak on circuit behaviour: the filter is a ladder with a soft clip, the chorus is a modulated delay.
- **PORT part from KR-106** (GPL-3.0, compatible in principle; see the "only or later" caution in section 8): (a) the OTA-tanh TPT ladder with one Newton step per stage (the file to read is `Source/DSP/KR106Voice.h`), (b) the DCO ramp curvature and discharge blip from `KR106Oscillators.h`, (c) per-voice tolerance, (d) the HPF shelf at position 0 (the "+10 dB below 150 Hz" detail is something the current engine may not have). The IR3109 is a four-stage OTA ladder (MEMORY), so KR-106's choice is structurally right; the quality still depends on the unread code.
- **Chorus:** build the BBD from Holters and Parker (paper) using BBDDelay (BSD-3-Clause) as the reference, then compare with KR-106's simpler Hermite-delay chorus and with Junox's. The MN3009 numbers in KR-106 (256 stages, 3.5 ms centre) are a cross-check for Junox's chorus.
- **No open Juno has been compared with a real 106** that I found. Juno60 (measurements of a real 60) remains the only real-unit data.

## 8. Licence consequences for an AGPL-3.0-or-later app

Compatible in principle and read: MIT (Open303, JC303's open303 files, OS-303, rusted-moog per SNIPPET), ISC (ImprovedMoog), BSD-3-Clause (chowdsp_wdf, BBDDelay, TR-707 driver file), Unlicense (MoogLadders and most of its filters), GPL-3.0-or-later (CA-72, Junox), AGPL-3.0-or-later (JC303's `dfl_*` files, andremichelle/tr-909), LGPL-3.0 (Huovilainen via MoogLadders, only if used as a separate piece or ported with notice).

Traps:

1. **GPL-3.0 "only" versus "or later".** KR-106, WaveDigitalFilters, WDR-8 and Surge XT all report SPDX `GPL-3.0` through the API, and the API does not distinguish "only" from "or later". If a file says "version 3 only", it can go into a GPLv3 section 13 combined work but cannot sit inside an "AGPL-3.0-or-later" licensed file. Read the header of each file before porting; write the actual wording in THIRD_PARTY.
2. **No licence means no right to copy:** schollz/juno-60 (also a derivative of GPL-3.0 Junox without carrying the licence), Faug, Yocto-V2.0, SuperOS-808 and the squares-and-circles repository (the API shows none, the README suggests MIT for the DrumSynth part). Use as ideas and published numbers only.
3. **WDR-8's licence is only in its README** ("GPL v3"); the API reports none. Ask the author or treat it as GPL-3.0-only to be safe.
4. **MoogLadders' per-file licences differ from the repo's Unlicense:** "Suggested CC-BY-SA" for the MusicDSP filter (share-alike terms do not map cleanly to AGPL; avoid), "Custom" for Simplified and Oberheim (no closed-source use; avoid), LGPLv3 for Huovilainen. ImprovedMoog (ISC) is already clean.
5. **MAME as a whole is GPL-2.0** (COPYING, READ). Only files that carry their own header such as `// license:BSD-3-Clause` can be used. GPL-2.0-only code cannot go into this app. The same applies to LMMS (API: GPL-2.0): read the per-file header.
6. **JC303 mixes four licences in one tree.** Take single files under their own header (the dfl files are AGPL-3.0-or-later, the rosic files MIT) and do not take the neural-overdrive port (GPLv3, GuitarML).
7. **CA-72 assets:** the code is GPL-3.0-or-later; the font is AGPL with an exception and the panel photograph is CC BY 2.0 and not included; neither belongs in this app's UI work.
8. **Non-commercial or no-derivatives terms:** I saw none among the code projects read. The Roland TR-909 software and ER-99 are closed. Sample packs on GitHub (Dirt-Samples, Sampled/Detroit) are a different question and out of scope.
9. **ROMs:** eh2k's README sends users to a third-party download of the 909 ROM dumps (hat, crash, ride). Whether those dumps may be used is a C1 and owner question; the licence status of Roland's data is not settled by any repo I read.

### 12.1 JC303's diode ladder: what it is, and whether to start from it

Files read (all under `midilab/jc303/main/src/dsp/open303/`): `dfl_DiodeLadderFilter.h` (1009 lines, 56,210 bytes), `dfl_DiodeLadderFilter.cpp` (7,177 bytes), `dfl_TB303OutputNetwork.h` (4,507 bytes), `dfl_LFO.h` (5,491 bytes), `LICENSE-AGPL-3.0` (AGPL v3 text), `LICENSE` (MIT, Robin Schmidt).

- **Exact licence header** (first two lines of both the ladder and the output network): `// SPDX-License-Identifier: AGPL-3.0-or-later` and `// Copyright (C) 2026 David Lowenfels`. The ladder's third line: `// Public interface modeled on rosic::TeeBeeFilter (Open303, MIT, Copyright (c) 2009 Robin Schmidt).` The JC303 root `LICENSE` is the GPL v3 text; the README's per-file list (section 2) puts the `dfl_*` files under AGPL-3.0-or-later. These two files are therefore usable in this app without any licence step-down.
- **Method** (quotes from the header comments): "4-pole diode ladder filter based on Will Pirkle's analysis" (AN-6); the stages are TPT one-poles ("y = z + g F"); "Every diode pair passes If tanh(dv / 2Vt)" in the default Hi-Fi mode, "solved per sample (stepHiFi)": "Two Newton steps from a linear extrapolation of the last two solutions, the 4x4 Jacobian (tridiagonal plus the feedback corner) by Cramer's rule". With Hi-Fi off, "only Q12 and Q21 saturate, around the linear ladder's zero-delay solve". No oversampling appears in the file (a grep for oversampling finds nothing); the nonlinearity is a tanh through chowdsp's `math_approx::tanh<7>` (math_approx is BSD-3-Clause, "Copyright (c) 2024, jatinchowdhury18", READ), with `rosic_RealFunctions.h` from Open303 (MIT) also included.
- **Circuit values and what is modelled:** four equal stage poles ("the TB-303's half-value bottom cap (C18) sees only one diode pair, so its pole matches the others"); a feedback coupling network with the C27/C25 corner into Q21's base (63.2 Hz at Q21 beta 300, 92.0 Hz at beta 200); the resonance pot as a loaded 50k linear pot with Open303's skew undone; loop gain K(pot, cutoff) "solved offline" from tables so that the resonant boost equals SPICE ("0.26 dB rms over the curves"); self-oscillation threshold from a growth test; the knob stops at about Q21 beta 500 because past it "the coupling network's ~7 Hz mode motorboats". Input drive stage with an asymmetric shaper (`setSaturationBias`), a ladder "rail" soft ceiling (`setRail`), Filter Feedback corner at 57.5 / 79 / 268 Hz for knob 1.0 / default / 0, mode morph LP to BP to HP by mixing stage taps, audio-rate cutoff modulation by per-sample coefficient update. The output path (`dfl_TB303OutputNetwork.h`): "Values from the TB-303 service notes; checked against SPICE (tools/diode-fidelity/spice/tb303_vca.py ...), within 0.25 dB above 20 Hz": C14 into the resonance pot (3.2 to 4.0 Hz), the VCA input summing R121 220k + C21 10n from the filter output and R122 100k + C22 10n from the pot wiper into 2.2k ("raises the level by up to 10 dB at full resonance"; wiper corner 140 to 156 Hz), and three subsonic poles fitted to SPICE "within 0.04 dB / 0.4 degrees, 2 Hz-2 kHz".
- **Validation claimed:** against the author's own SPICE netlists only ("SPICE large-signal response within 0.04 dB / 0.02 % THD rms at the 303's level"; Newton solve "within -90 dB of a converged solve on stress tests"). The `tools/diode-fidelity/` scripts that generate the tables and netlists are NOT in the file set I could read (paths are named in comments; the directory is probably in the author's tree, unconfirmed). "Component tolerances make real units differ mostly by such a scale (spice/mc_native.py)" shows a Monte-Carlo tolerance check. No comparison with a real 303 is stated.
- **Real-time cost:** the header says Hi-Fi matches SPICE "for about 6 % more CPU per voice" than the non-Hi-Fi mode; no absolute figure. Arithmetic per sample: two Newton steps, each a 4x4 near-tridiagonal Cramer solve, several tanh. For one mono voice at 44.1 or 48 kHz in JS doubles this is cheap (my estimate, MEMORY; no benchmark was run).
- **Independent cross-check:** a1k0n/303 (12.5 below) measured a real x0xb0x (same analogue section as the 303) with an oscilloscope and found the diode ladder "works almost exactly like the theoretical model says it should, except for a high-pass filter in the resonance feedback loop": the same finding JC303's feedback network encodes (about 100 Hz in a1k0n's code, 63 to 92 Hz here).
- **Better starting point than the Open303 TeeBeeFilter the app uses now?** Yes for filter and output path: it carries real component values (C27/C25, R121/R122, C21/C22, C14), the resonance feedback high-pass, Q21 and Q12 saturation, and the output network that Open303 replaces with "fitted allpass / highpass / notch chain" (the output network's own comment). Reservations: single author, 2026, only SPICE-validated, no tests or issues read, and its author's SPICE sources are not in what I read. Keep Open303 for oscillator, envelopes, accent and slide.
- **What porting to JS involves:** (1) `dfl_DiodeLadderFilter.h/.cpp` (about 64 KB of C++ with `INLINE` macros) into one JS class in `classics-processor.js`; (2) `dfl_TB303OutputNetwork.h` (about 4.5 KB, plain biquad/one-pole cascades) as a second class; (3) replace `math_approx::tanh<7>` (a polynomial/rational tanh: write one, or reuse the app's Pade tanh) and the two or three `rosic_RealFunctions` calls; (4) no JUCE, no SIMD; (5) the Open303 interface the header copies (`setCutoff`, `setResonance`, `getSample`) matches the app's existing TeeBee wrapper, so the swap sits behind a mode flag; (6) check sample-rate scaling (the filter takes `setSampleRate`), and the audio-rate cutoff update per sample. Add a THIRD_PARTY row with the exact header text above. Effort: a few days with a bench; start by diffing the app's TeeBee output with the port at the same knob settings.

- **Layout (README table, READ):** `crates/ca72` (real-time models and the voice), `ca72-plugin` (nih-plug and editor), `ca72-panel`, `ca72-lab` (ngspice benches, calibration, reference measurements), `ca72-spice` (runs ngspice netlists and reads results), `ca72-analysis`, `ca72-rt` (threads), `circuits/` (transcribed netlists and device models: `circuits/boards/board4-vcf.lib`, `board4-vca.lib`, `board4-preamp.lib`, `board4-a440.lib`, and `circuits/models/`; the other board files by name were not fetched), `docs/circuit/` (board1 to board4 and voice, numerics, components, assumptions), `docs/decisions.md`, `docs/history.md`. `crates/ca72/src/lib.rs` declares modules `a440, contour, devices, expo, fast, filter_cal, freq_dial, keyboard, light, linear, mna, modulation, noise, preamp, pulse, resample, revsaw, tables, threaded, tuning, ulp, unconverged, vca, vcf, vco, voice` among others; `mna.rs` (75 KB) is a modified-nodal-analysis solver. Its only dependency is `libm` ("Transcendental functions come from libm, so renders are the same on every platform"); `crates/ca72` has no GUI or plug-in dependency.
- **How the ngspice checks work:** the lab transcribes each board's netlist from service documents (sources and hashes in `docs/circuit/sources.md`; `scripts/fetch-sources.sh` downloads them, they are not in the repo), runs ngspice 47 benches, and `cargo test -p ca72-spice -p ca72-lab` compares the real-time models with the results; tests say SKIPPED without ngspice unless `CA72_REQUIRE_NGSPICE=1`. Stated agreements (plan.md, READ): oscillator pitch "within 1 cent on every key and range", 0.088 cent on 32' to 2', harmonics within 1 %, aliasing -70 dB at 4 kHz; filter "small-signal within 0.25 dB to 10 kHz, self-oscillation within 3 cents and 0.04 dB, drive distortion within 0.33 dB", exponential converter "within 0.1 cent over CUTOFF and temperature"; contours within 27 to 72 mV of ngspice over five scenarios. Then the hardware-reference calibration (a modern recreation, as the coordinator confirmed).
- **Which quality can run in a browser:** only the light model. README Limitations (READ): the circuit's model (HI) and High Fidelity (ULTRA) "do not run in real time on most computers (R48): one or two voices split over six threads each come close on a machine of 6 or more fast cores". QUALITY LO ("Potato mode") uses `ca72::light::Light` (`crates/ca72/src/light.rs`), whose doc says it is "Not derived from the circuit but fitted to the circuit model's measured behaviour", "allowed to sound worse than the circuit's" (decisions R47). README: LO is "close to the circuit, not the same" (R47), ten voices cost "a quarter to a seventh of HI's on one thread (about a fifth of a core of a fast computer, a Ryzen 7 7800X3D)"; decisions line "LO costs more than R-LO-DEFAULT says ... 18 to 21 % of a core for ten voices ... (R71's filter at 8x since)". For the app's monophonic Model D that is roughly 2 % of a fast core per voice (my division).
- **Why the light model suits an AudioWorklet:** per `light.rs`: single-precision audio path, "Nothing here allocates once made", band-limited BLEP/BLAMP oscillators, the filter at `FILTER_OVERSAMPLE = 8` times the voice rate, control laws updated every `CONTROL_EVERY = 16` samples, and "The stages, public" (R-LIGHT-STAGES): `Osc`, `Noise`, `Ladder`/`LadderFilter`, `Contour`/`ContourLaw`, `Vca` are exposed as separate modules "for an instrument that uses each as a module of its own (Olifant, Idle Foundry's modular synthesizer)". `Ladder::tick` (READ): four trapezoidal one-pole stages, the loop solved without delay for a nonlinear input pair (tanh through the pair's limit), by Newton with a bracketing fallback, up to 24 iterations per sample, residual 1e-6; the filter loop's non-convergence is counted, not fatal.
- **What "port part" means, in order:** (1) the laws, as data: `light.rs` functions `channel`, `knob_current`, `contour_current`, `node_log2`/`cutoff_points`, `emphasis_law`, `ladder_coefficients`, `passband`, `ring_lift`, `pair_limit`, `drive_top`, `vca_gain`, `pitch_offset`, `oscillator_increment`, plus the table constants and `laws::` in the same file and `voice.rs` helpers (`cutoff_track`, `emphasis_r14`, `time_pot`, `glide_r`, `volume_track`, `contour_amount_track`, `sustain_track`, `ext_taper`): these replace the app's CA-72 knob-law numbers with the full functions. (2) `Osc` and `Noise` (BLEP/BLAMP tables from `resample.rs`, 23,686 bytes). (3) `Ladder` and `LadderFilter` with the 8x oversampler (`resample::Decimator`/`Interpolator`): the heavy part, 8 filter evaluations with a Newton solve per output sample. (4) `Contour`/`ContourLaw` (RC segments, trigger 11.5 ms re-arm, `laws::TRIGGER_ON/OFF/REARM`) and `Vca`. (5) The `Light` voice: lowest-note priority, single triggering, glide. A Rust to wasm32 build (the crate has only `libm`; `unsafe_code = "deny"` workspace-wide; no threads needed for one voice) is the lowest-risk route; a hand port to JS of about 4,000 lines of Rust is the alternative. Not tested by me: that the crate compiles to wasm32-unknown-unknown with Rust 1.97 and edition 2024 (MEMORY: it should).
- **Not worth porting:** `vcf.rs` (96 KB), `mna.rs`, `preamp.rs`, `vca.rs` heavy forms, `threaded.rs`, `ulp.rs`: the circuit-level solve that cannot run in real time in a browser. Use it offline as a reference for the app's bench (render the same patch with the app's Model D and with CA-72 under `ca72-lab play`).
- **Licence consequence:** GPL-3.0-or-later into AGPL-3.0-or-later is fine; add the THIRD_PARTY row naming `light.rs` and the workspace licence line. Credits and the font/photo caveats from section 6 stand.

### 12.3 KR-106: filter, DCO, tolerance, firmware model, and licence per file

Read (all `kayrockscreenprinting/ultramaster_kr106/main/`): `LICENSE` (GPL v3 text), `README.md`, `THIRD_PARTY_LICENSES`, and in `Source/DSP/`: `KR106Voice.h` (1,442 lines), `KR106VCF_OPTIMIZED.h` (16,267 bytes), `KR106Oscillators.h` (253 lines), `KR106Chorus.h` (805 lines), `BBDFilter.h` (121 lines), `KR106ADSR.h`, `KR106VcfFreqJ106.h`, `J106DACHzTable.h`, `KR106Resampler.h`, `KR106_DSP.h`, `PluginProcessor.cpp`.

- **Licence per file:** the repo statement is "This project is licensed under the GNU General Public License v3.0" (README line 130) with the GPL v3 text in `LICENSE`. I grepped the files above for SPDX, GPL, licence and copyright and found no per-file header in any of the DSP files: so the only statement is GPL-3.0 for the project, with no "or later" wording. Treat all KR-106 code as GPL-3.0-only unless the author says otherwise; `THIRD_PARTY_LICENSES` lists JUCE (used under AGPLv3), the VST3 SDK (MIT) and others, not relevant to the DSP headers, which include only `<cmath>`, `<algorithm>` and each other (no JUCE). Consequence for an AGPL-3.0-or-later app: GPLv3 section 13 lets the two be combined, but the KR-106-derived files would stay GPL-3.0 (no "or later"), so the combined app could only be distributed under AGPL-3.0 for that portion; note it in THIRD_PARTY, and ask the author for "or later" if wanted.
- **The code has moved on from the doc I read in section 5.** `KR106VCF_OPTIMIZED.h` is the filter now: a "BA662 feedback architecture — circuit-accurate OTA model", with the schematic's resistor values in its header (input 10K to the filter node, 47K to the OTA +IN, 100K from filter output to OTA -IN, 1.5K to ground: input attenuated 0.0309, feedback 0.0148), a per-stage OTA tanh (IR3109 model), supporting 1x, 2x or 4x oversampling with the caller driving `ProcessSample` at that rate, a control-rate `UpdateCoeffs(frq, res)` and an audio-rate `ProcessSample`; Newton-Raphson "one iteration from the linear TPT estimate" per stage. `KR106Voice.h` carries `mOversample = 4` by default and says the PolyBLEP oscillator runs at the oversampled rate.
- **DCO:** `KR106Oscillators.h` (PolyBLEP saw, pulse, sub, noise; the curvature `1 + 0.15 (1 - pos)` and the discharge blip documented in the DSP doc) plus `KR106OscillatorsWT.h` (wavetable option). Not read in detail.
- **Tolerance:** `KR106Voice.h` `kNumVarianceParams = 5`: VCF FRQ (±750 DAC counts, 1143 DAC counts per octave), VCF WIDTH (±100 cts/oct), VCA (±12 % gain), PW Lo (±5 around 50 %), PW Hi (±5 around 95 %), with "Human" ranges (±10 cts/oct width, ±2 PW) and a `kVoiceSlotMap` that maps six voices to physical DAC slots. This replaces the DSP doc's table (cutoff ±5 %, pitch ±3 cents, envelope ±8 %) quoted in section 5: the code is richer than the doc.
- **Firmware-level model of the 106:** `KR106VcfFreqJ106.h` is "Clean-room reimplementation of the D7811G firmware's VCF cutoff frequency calculation ($04D5–$064E). All arithmetic is uint16_t with explicit carry/borrow tracking, matching the uPD7811's 16-bit EA register pair"; `KR106ADSR.h` "Reproduces the D7811G ROM table (0D60_envDecRelTbl)" with "ROM-accurate D7811G digital envelope generator, reverse-engineered" and a mode switch for the Juno-6/60 analog RC envelope (`kJ6`, `kJ60`, `kJ106`). `J106DACHzTable.h` holds "kV4Hz: output frequency (Hz) of voice card V4 at every 12-bit DAC code 0..4095", from 93 measured DAC codes with log-linear interpolation, gain-calibrated "so DAC=1568 reads exactly 248.000 Hz" and bit-flip steps at DAC 1024 (-4.64 cents), 2048 (+23.31 cents), 3072 (-4.48 cents). This is measurement of a real Juno-106 voice card, and the only firmware-level (D7811G) Juno-106 model I found anywhere. Caution: how the author obtained the firmware logic (a ROM disassembly) is not stated in what I read, and Roland's firmware is copyrighted; "clean-room" is the author's word. The 4,096-double table costs 32 KB.
- **Chorus and BBD filter:** `BBDFilter.h` says "ngspice simulation confirms Juno-6 and Juno-60 prefilters", "Error vs ngspice: ±0.5 dB from DC to 15 kHz" with a frequency table; `KR106Chorus.h` (805 lines) includes `KR106AnalogNoise.h`. Not read beyond the header. The DSP doc's 256-stage, 3.5 ms description is the earlier version; verify against the code before using numbers.
- **Verdict for the Juno block:** the filter (`KR106VCF_OPTIMIZED.h`, with the schematic's values in comments), the DAC-count cutoff law and the measured V4 table are what to port, after reading each body; the firmware ADSR table is the strongest finding for envelope timings since it is the real 106's integer arithmetic. Licence: GPL-3.0 with no "or later" stated.
